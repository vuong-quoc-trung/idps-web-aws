# R47 · First AWS deployment

## Source and architecture

The integration branch takes the 22 commits from `origin/dev/i5-hybrid-prevention` at `798e66a462dd29426772146bff7c02ad6acead1f` through merge `8265ea07e0d481879807b607d1ac7fc93be17ee8`. The worktree retained R46, its certificates and gateway acceptance. The review also covered the HTTPS, AI shadow, Suricata proxy and simulator branch refs. The merge brings forward the Student authentication and audit work, Rust realtime dashboard with authenticated SSE, Rust Hybrid review and the current database migrations. The deployment profile keeps the latter's enforcement dependencies out of the AWS startup path.

- NGINX terminates TLS and sends Student API traffic to Java on `127.0.0.1:8080`. It generates the request ID at the edge and serves the built Student UI. AWS returns Security Web through the Rust listener on `127.0.0.1:3000`.
- PostgreSQL 18 uses separate owning roles and databases for Student and Security. Java writes Student Audit to a private ownership group. Rust reads log sources and stores evidence in its own database. Its SSE and management APIs require authentication.
- R37 HGB URI100 is the frozen research scorer. The service listens on a Unix socket and restricts its peer to the NGINX worker UID. Rust can ingest the resulting research journal. The default R47 gateway routes Student traffic directly to Java. Completion of the private Suricata AF_PACKET/Lua proof leg and its evidence bridge requires separate acceptance on this topology.
- Rust runs with `ENFORCEMENT_MODE=OFF`, `AUTO_BLOCK=false` and a disabled firewall command. The staging security group exposes the R46 web ports. SSM remains the administrative channel. R46 Auto-Stop was deferred.

## Build and operation

1. Build the frozen source revision with the committed package lockfiles. Run `npm ci && npm run build` in `student-web/frontend` and `security-web/frontend`. Package the Java backend with the Maven wrapper and build `cargo build --release --locked --bin pbl4-security-demo` from `security-web` using an x86-64 GNU/Linux toolchain compatible with Ubuntu. Verify the published Beta.2 checksum and use its existing scorer release, including its own manifest and both model slots.
2. Stage `student.jar`, `student-ui/`, `security/pbl4-security-demo`, `security/dist/`, `scorer/`, `install.py` and `cloud_profile.py` in a private directory. Generate `r47-files.json` mapping relative artifact paths to SHA-256, excluding the manifest itself. Archive and verify an outer SHA-256 independently before unpacking on the target.
3. On the pinned staging instance, use SSM and verify Ubuntu, IMDSv2, the R46 gateway digest and exclusive ownership of the installation window. Install PostgreSQL 18, Java 25 and ACL tooling from Ubuntu. Keep PostgreSQL listening on loopback. The [installer](../security-web/deploy/aws-r47/install.py) accepts `--bundle`, `--revision`, `--account` and `--instance`. It is for an empty staging install. For an update, first verify and back up both databases and the active release; stage the new revision beside the active one, check migration compatibility and test before switching the service paths.
4. The boot order is PostgreSQL, Student and Security application services, scorer after cloud admission, and NGINX routing to the enabled applications. Check `systemctl status websentinel-r47-{student,security,scorer}`, `postgresql@18-main`, `nginx` and `journalctl -u <unit>` via SSM. Root-only bootstrap credentials were generated on the target. Keep them out of command output, ticket systems and Git. Use a separate credential rotation process when handing access to an operator.
5. For gateway rollback, validate the original R46 SHA and restore `/etc/websentinel-r47/nginx-r46.backup` to the R46 gateway path, run `nginx -t` and reload. Stop only the R47 application units if necessary and retain the databases. R36 remains pinned in the scorer manifest; selecting it requires a deliberate setting in `scorer.env` and a health check against the rollback digest. For normal EC2 start/stop, confirm the AWS identity and exact instance, use SSM, and verify state after stop. [AWS staging operations](AWS_STAGING_OPERATIONS_HANDOFF.md)

The [cloud resource profile](../security-web/deploy/aws-r47/cloud_profile.py) verifies the EC2 account, instance, Region, type, architecture and DMI via IMDSv2, then binds a root-owned marker to the current boot. Physical CPU thermal telemetry is not applicable on this instance. The separate Local thermal guard stays in place. The Linux slice reserves up to 1.5 vCPU and 6 GiB for R47; the scorer is capped at 0.25 vCPU, 768 MiB, 64 tasks and no swap. Supervision checks kernel readback, ownership, pressure telemetry, OOM counters, disk headroom and the systemd watchdog. User-facing traffic does not depend on the scorer.
